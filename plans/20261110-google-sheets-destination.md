> ## Goal
> Add "Google Sheets" as a delivery destination alongside the existing webhook, so every new GridPane alert is appended as a row to a Google Sheet that the extension creates itself. The sheet is read by other tools (Claude, through the Google Sheets connector) to follow GridPane activity such as clone/migration "Process Complete" notices, because Claude in Chrome cannot read chrome-extension:// pages.
>
> ## Decided approach (keep these)
> - The extension writes directly to the Sheets API. No Apps Script and no public web app: auto-deploying a script needs a manual "Apps Script API" toggle plus a first-run authorization, and the web app URL would be public with no signature check.
> - Auth: chrome.identity.getAuthToken with the single scope https://www.googleapis.com/auth/drive.file (non-sensitive: the extension can only see files it created, so no Google verification is needed). Manifest gains the "identity" permission, an "oauth2" block with the client_id, and host permission https://sheets.googleapis.com/*.
> - Settings card "Google Sheets": a Connect Google Sheets button (interactive token, then spreadsheets.create titled "GridPane Alerts" with a frozen header row), the linked sheet's URL with an Open link, a Disconnect button (chrome.identity.removeCachedAuthToken, clear the stored id), a Send test row button, and a "Also send alerts found during a full history import" checkbox mirroring webhookIncludeBackfill.
> - Columns: created_at (ISO), severity, title, message, server_label, server_ip, site_url, team_id, alert id, action_url, sent_at. Build each row from webhookPayload(rec, lookups, 'full').notification in normalize.js; add a pure sheetRow() helper there with Node tests.
> - Delivery reuses the outbox and backoff in background.js (storeNew → outbox → flushOutbox / doFlush). Track delivery per destination so the webhook and the sheet retry independently; one failing must not block or duplicate the other. Batch due rows into a single values.append call (valueInputOption RAW, insertDataOption INSERT_ROWS), oldest first. On a 401, refresh the cached token once; on a 429, back off using Retry-After, as gpGet already does. Never re-append a row that was already appended (keep a per-alert sheet-sent marker).
> - Migrate existing outbox records safely (they currently mean "webhook pending").
> - The sheet is opt-in; with it off, webhook behaviour is unchanged.

- **Approach / Architectural Fit:** The extension already has exactly the two things Sheets needs: an outbox with per-record backoff and a place to shape a plain-text alert (`webhookPayload(...).notification`). Keep that path and add a second destination beside it. A standalone `lib/sheets.js` owns the OAuth scope, the spreadsheet/tab names, the 11-column schema, the A1 ranges and the URL builders, so the header, the row and the append range cannot drift apart; `normalize.js` adds `sheetRow()` and maps `webhookPayload(rec, lookups, 'full').notification` onto `SHEET_COLUMNS`, so the sheet uses the same resolved server/site names and ISO timestamp as the webhook. A standalone `lib/outbox.js` owns the migration from the current webhook-only record to `{ webhook: {...}, sheet: {...} }` and the due/sent/failed transitions, so Node can prove the two destinations retry independently while Chrome integration stays in `background.js`. The interactive OAuth token is requested from the Connect click in `app.js`, where Chrome still sees a user gesture; the service worker uses the cached token for flushes and never persists it. The manifest carries `identity`, the `oauth2` block with the exact `drive.file` scope, and the Sheets host permission. **Connect** creates the spreadsheet, writes the header with `valueInputOption=RAW` (so alert text beginning with `=` is stored literally, not evaluated) and freezes row 1 with `batchUpdate`; only after all three calls succeed are the id and URL saved. Delivery is opt-in and reuse the outbox: `storeNew` queues a fresh alert for either destination, and `doFlush` handles each destination on its own gate, attempt count and `next_at`, so one failure cannot block or duplicate the other. Due sheet rows are appended oldest first in one `values.append` per batch (capped at 500 rows) with `valueInputOption=RAW` and `insertDataOption=INSERT_ROWS`. A per-alert marker in a new DB v3 `sheetsent` store prevents a re-append; the marker is written after a successful append, and before each append the outbox records `attempted_at`, so the only case that needs a reconcile read of `Alerts!I2:I` is a service-worker kill or network timeout between the append and the marker write. A 401 removes the cached token, fetches a new non-interactive token and retries once; a 429 is a typed error whose `Retry-After` feeds the same backoff used by the webhook. Sheet failures are recorded in `state.lastSheetError` and the sync log, never in `state.status`, so a Google problem cannot pause GridPane sync. With the sheet off, every new branch is skipped and the webhook path is unchanged. Connecting a sheet deliberately does not copy the existing archive: only alerts stored after the connection (plus not-yet-stored alerts found during a history import with the checkbox on) are appended. `docs/PRIVACY.md` and the store listing must say that alert text is written to a spreadsheet in the user's own Drive through Google, that the extension only sees files it created, and that the sheet remains after Disconnect.

### Assumptions (marked, veto any of these before execution)

- **The real OAuth client_id is supplied before Phase 2.** The Google Cloud project, consent screen and Chrome-extension OAuth client are human setup; the plan does not invent a client_id. The value is public and committed in `manifest.json`, but a `REPLACE…`/empty value fails the Phase 2 validation, so the executor stops and asks rather than shipping a broken Connect button.
- **Only `https://www.googleapis.com/auth/drive.file` is requested.** No `drive`, `spreadsheets` or other Google scope is added, so the extension cannot see files it did not create and no Google verification review is needed.
- **`package.mjs` enforces the scope too.** A broader or extra `oauth2.scopes` entry fails `node scripts/package.mjs --check`, so the scope rule is a build gate rather than only a review note.
- **One spreadsheet and one tab:** title **GridPane Alerts**, tab **Alerts**, 11 columns A:K, header row frozen. The title, tab name and columns are not user-configurable in this version.
- **Connect reuses the stored spreadsheet when it is still readable, otherwise creates a new one.** There is no existing-sheet picker, and a new sheet is not automatically shared with anyone.
- **Two new runtime files:** `lib/sheets.js` and `lib/outbox.js` are added to `RUNTIME_FILES`. `sheetRow()` stays in `normalize.js` as requested; it imports the column list from `lib/sheets.js`.
- **The outbox record shape changes, with a safe migration.** A legacy record (no `webhook`/`sheet` keys) becomes a webhook-only record; no notification, outbox id or created_at is lost, and a legacy row is never sent to the sheet.
- **A per-alert marker lives in a new DB v3 `sheetsent` store**, pruned to the newest 5,000 ids. The marker plus an `attempted_at` stamp and a reconcile read after an interrupted append is what makes "never re-append" true; the reconcile read does not run on the normal path.
- **At most 500 rows per append** (`SHEETS_BATCH_MAX`). A larger backlog takes more than one call in the same flush; the order stays oldest first.
- **`sheetsIncludeBackfill` mirrors `webhookIncludeBackfill` and defaults to off.** Connecting a sheet does not copy the existing archive; only new alerts, plus not-yet-stored alerts found during a history import with the checkbox on, are appended.
- **Disconnect drops pending sheet halves and clears the marker store.** The spreadsheet itself stays in the user's Drive and is deleted there by the user.
- **Sheet failures do not change `state.status`.** They surface in `state.lastSheetError`, the Settings card and the sync log; GridPane sign-out and 429 handling are untouched.
- **The interactive Google token is obtained in `app.js` from the Connect click**, then passed to the service worker for the create calls. The background uses `getAuthToken({ interactive: false })` for flushes and never stores the token itself; Chrome's identity cache holds it.
- **The manifest description and the store listing summary both mention Google Sheets**, remain equal, and stay within the 132-character limit. `dataUse.authenticationInfo` stays false because Chrome, not the extension, holds the OAuth token; the listing note discloses the Google connection.
- **The unpacked extension ID is a development detail.** A `key` may be added locally to pin it to the OAuth client, but it is never committed or shipped (`package.mjs` rejects it); the README also documents a second OAuth client for the Web Store-assigned ID.
- **The expected release version is 1.4.0.** Phase 2 writes it into the manifest and Phase 4 into the README tag example, so the feature branch is ready for a 1.4.0 release; the `git-squash-release` run, tag and upload remain outside this plan.

## Summary

Abandoned on 2026-11-11 before Phase 2. The Google Sheets destination required a Google Cloud project, an enabled Sheets API, a published OAuth consent screen and a store-bound OAuth client; that setup and the distribution overhead were not worth it for this extension. Phase 1 (the pure sheet/outbox models and `sheetRow()`) was committed on `feat/google-sheets-destination` and then removed with the branch, so no code from this plan remains on `main`. No webhook, sync, storage or UI behaviour changed.
